# 환류관리 모듈 상세설계 (초안 v0.1) — ★제안 차별화 핵심

> [A대학교] 교육 수요자 만족도 통합조사 플랫폼 / 작성 2026-08-07
> 근거: 제안요청서 IV.2.라 "환류 관리 특화 요구사항" + SFR-009/010 + 기대효과 다.
> 전략 근거(CLAUDE.md B-4): 정성평가 80점 중 환류 상세설계가 킬러. 타 업체는 설문·통계까지만 흉내내고 환류는 얕게 다룸. 여기서 점수 벌린다.

## 0. 왜 환류가 핵심인가 (제안서 '사업 이해도'에 반영)
- 발주 배경 = 부서별 산발 조사 → **통합 + "조사 결과를 실제 교육품질 개선으로 연결(환류)"**. 즉 학교가 진짜 원하는 건 "설문 도구"가 아니라 **PDCA 루프의 시스템화**.
- RFP가 환류를 별도 요구절(라.)로 뗀 유일한 기능군 → 배점 의도가 분명.
- 우리 강점: 회사가 성과진단·실태조사([A시] 교육발전특구, [A대학교] 성과진단) 수행 이력 → **"진단 후 개선관리"를 업으로 해온 회사**라는 서사와 연결.

## 1. 환류 업무 흐름 (PDCA 매핑)

```
[조사 종료·결과 확정]
      │  ① 문항/영역 → 담당부서 자동 매핑 (FB_Q_DEPT_MAP)
      ▼
[Plan] 부서담당자: 원인분석 + 개선권고 확인 + 향후 개선계획(예산·일정·실행방안) 입력  (FB_PLAN)
      │  ② 부서별 권한분리 — 본인 부서 과제만
      ▼
[Do]   부서: 개선 실행 (연중)
      ▼
[Check] 차년도 조사 시점: 전년 '개선계획' 대비 '실행 완료여부' + 증빙 업로드  (FB_RESULT, FB_EVIDENCE)
      │  ③ 전년 과제와 연계(FB_TASK_LINK) → 이행점검
      ▼
[Act]  개선효과를 차년도 조사결과(점수 변화)와 비교분석 → 대시보드 반영  (SV_STAT_SUMMARY 연도비교)
      └─(루프) 미달 과제는 다음 연도 과제로 이월
```

**RFP 요구 4개 항목 ↔ 설계 대응**
| RFP 라. 요구 | 설계 반영 |
|---|---|
| 문항별 매칭 담당부서로 개선권고 자동 분류·전송(자동 어려우면 수작업 가능) | FB_Q_DEPT_MAP + 결과확정 배치가 부서별 과제 자동생성. AUTO_YN='N'이면 운영자 수동 배정 UI |
| 부서관리자 전용 페이지: 원인분석·개선권고·향후계획(예산/일정/실행)·실행결과·증빙 입력 | 부서담당자 환류 입력화면(FB_PLAN/FB_RESULT/FB_EVIDENCE), 역할=부서담당자 |
| 차년도: 전년 개선계획 대비 실행완료 여부·증빙 업로드·이력관리 | FB_RESULT.CHECK_YEAR + FB_TASK_LINK(FROM_TASK_ID=전년/TO_TASK_ID=금년) 이력 |
| 개선과제 DB 연도별 연계, 과거-현재 비교분석 구조 | FB_TASK.SURVEY_YEAR + FB_TASK_LINK 체인 + 연도비교 뷰 |
| 부서담당자는 본인 부서 과제만 조회·입력(세밀 권한) | CM_USER_ROLE.DEPT_ID 스코프 + FB_TASK.DEPT_ID 필터 (행 수준 보안) |

## 2. 상태 전이 (개선과제 FB_TASK.STATUS_CD)

```
 (생성)──▶ 등록(REG) ──▶ 계획수립(PLANNED) ──▶ 진행(DOING) ──▶ 완료(DONE)
                │                                    │
                └──────────▶ 반려/보류(HOLD) ◀───────┘
 완료 후 차년도 점검 결과:
   달성(ACHIEVED)  또는  미달→이월(CARRIED) ──▶ 다음연도 신규 FB_TASK 생성
                        + FB_TASK_LINK(FROM_TASK_ID=전년, TO_TASK_ID=금년, LINK_TYPE_CD='이월') 연결
```
> STATUS_CD 값 집합(정본 정합): 등록(REG)/계획수립(PLANNED)/진행(DOING)/완료(DONE)/달성(ACHIEVED)/이월(CARRIED)/보류(HOLD). 연도 연계는 FB_TASK에 컬럼을 두지 않고 **FB_TASK_LINK 테이블로 일원화**(정본 설계_01 §3-9).

- 상태별 담당: 등록=결과확정배치/조사운영자, 계획수립·진행·완료=부서담당자, 점검=조사운영자+부서담당자.
- 알림: 상태 변경 시 담당자에게 통지(포털 알림/이메일 — SFR-002 최근 알림 연동).

## 3. 화면 설계 (환류 모듈)

| 화면 | 역할 | 주요 기능 |
|---|---|---|
| 환류 대시보드 | 관리자/운영자 | 부서별 과제 현황(등록/진행/완료/미달), 이행률, 연도별 개선 추이 |
| 문항-부서 매핑 관리 | 관리자 | 문항/영역별 담당부서 지정, 자동/수동 전환 |
| 개선과제 목록 | 운영자/부서담당자 | (부서담당자는 본인부서만) 과제 검색·필터(연도/조사/상태/부서) |
| 개선계획 입력 | 부서담당자 | 원인분석·개선권고 확인·향후계획(예산/일정/방안) 입력, 임시저장 |
| 실행결과·증빙 입력 | 부서담당자 | 실행완료 여부·결과·증빙파일 업로드 |
| 차년도 이행점검 | 운영자 | 전년 계획 대비 실행 대사, 달성/미달 판정, 이월 처리 |
| 연도별 비교분석 | 운영자/관리자 | 동일 문항·영역의 연도별 만족도 점수 vs 개선과제 이행 상관 |

## 4. 핵심 로직 상세

### 4-1. 결과확정 → 개선과제 자동생성 (배치 or 버튼)
```
조사 STATUS='완료' 확정 시:
  FOR each (문항/영역) IN 조사:
     dept = FB_Q_DEPT_MAP 조회 (없으면 미배정 큐 → 운영자 수동배정)
     IF 만족도점수 < 임계값(설정) OR 개선필요영역 THEN
        newTask = INSERT FB_TASK (조사, 연도, 문항/영역, dept, STATUS='등록')
        prev = 전년 동일 문항/부서 과제 조회
        IF prev 존재 THEN
           INSERT FB_TASK_LINK (FROM_TASK_ID=prev, TO_TASK_ID=newTask, LINK_TYPE_CD='이월')
```
- 임계값(예: 5점 척도 3.5 미만)은 공통코드/설정으로 관리 — 학교와 협의(SFR-008 "협의하여 확정").

### 4-2. 부서 행 수준 보안 (라. 세밀 권한)
```
개선과제 목록 조회 SQL 표준:
  WHERE FB_TASK.SURVEY_YEAR = :year
    AND ( :isAdmin = 'Y' OR FB_TASK.DEPT_ID IN (:myDeptIds) )
```
- `:myDeptIds` = CM_USER_ROLE에서 로그인 사용자의 담당부서(하위부서 포함 옵션).

### 4-3. 연도별 연계·비교 (라. 과거-현재 비교)
- FB_TASK_LINK 체인으로 같은 문항·부서 과제를 연도 순 연결.
- 비교 뷰: 전년 계획(FB_PLAN) ↔ 금년 실행(FB_RESULT) ↔ 조사점수 변화(SV_STAT_SUMMARY 연도 diff).

## 5. 발표 데모 시나리오 연결 (참고 — PPT/발표용)
1. 관리자: 만족도조사 결과 확정 → 저조 문항이 자동으로 담당부서(예: 학생지원팀) 과제로 생성되는 장면.
2. 부서담당자 로그인 → **본인 부서 과제만** 보이는 화면(권한분리 시연) → 원인분석·개선계획 입력.
3. 이듬해: 전년 계획 대비 실행결과 입력 + 만족도 점수 상승 그래프 → "조사가 개선으로 이어지는 루프" 시각적 증명.
- 이 3장면이 정성평가위원에게 "이 회사는 환류를 진짜 이해했다"를 각인.
